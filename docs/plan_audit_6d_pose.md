## 0. 结论先讲

1. 方案列的四个新模块里，**三个已经在代码里**（高度约束、跨板联合、机械约束降维 + 1D yaw 精修），
   其中**一条（EKF 相位转换）照做会双重计相位、直接倒退**。
2. 真正缺的只有三件：**2D 优化求解器**、**时间戳/检测精度**、**板编号模块化**。
3. 而"2D 优化"有一个**前置门**，方案没有提：它的 ψ 来自拟合器，而拟合器 yaw 的精度
   **完全由拟合质量分层**——本轮实测（同一份实车检测流）：

   | 拟合 rmse | 样本 | 与 EKF yaw 的差（模 90°） |
   |---|---|---|
   | < 3 px | 312 | 中位 **+0.49°**、p10/p90 −0.08°/+0.93°、**std 0.57°** |
   | 3–8 px | 223 | 中位 +1.21°、std 9.7° |
   | 8–16 px | 1185 | 中位 +5.67°、std **22.6°** |

   也就是说：**方案里 σ_ψ ≈ 0.5–1° 的假设成立——但只在 rmse < 3 px 那 18% 的拟合上成立。**
   而当前配置的门限是 `max_rmse_deg = 0.4°`，在 fx=2399 下等于 **16.7 px**，
   恰好把 σ_ψ = 22° 的那一大坨放进了 yaw 注入通道。这解释了 yaml 里那句
   "直接注入会让慢转工况从 0.3px 劣化到 30px"。

   **所以要先把门控收掉，2D 优化才有意义。**

## 2. 需要更正的地方

### 2.1 `Z` 的语义混了（最重要，直接影响 2D 优化的正确性）

方案 §4.3 自己写了这个疑点（"拟合器的 `Z` 是旋转中心的深度，而 `t_z` 是装甲板中心的深度"），
但在 §5.2 又按 `t_z = Ẑ` 直接把问题降到 2D。这两者相差
`[R_cv · R(θ) · p_armor_v]_z`，量级 `R·|sinθ|`：**R = 0.2 m、θ = 90° 时就是 20 cm** ——
比方案自己写的 σ_Z = 1–5 cm 大一个数量级，也比 4D PnP 的 ~20 mm 差。

正确做法是用拟合器输出的**完整刚体** `(C, θ, R, h, α)` 反算板心深度：

```
t_z = C_z + [ R_cv · ( (R − b·sinα)·n̂ + a·t̂ + (h + b·cosα)·ẑ ) ]_z
```

（本项目里就是 `barEndpointV` + `vehicleToCamera` 那两段；2026-10-11 的合成自检正是这样把
真值参数投影成端点、再回灌验证的。）

**在没改这一点之前上 2D 优化，会把"旋转中心深度"的误差直接灌进 `t_x, t_y`。**

### 2.2 拟合器的 yaw 精度不是常数，是被质量门控的

见 §0 的表。补充两条：

* 分层看下来，残差的中位是稳定的（四段的 yaw-offset 中位 0.4°/0.5°/0.8°/1.8°，漂移 < 1.5°），
  也就是说**它是一个"常值偏差 + 与拟合质量成反比的噪声"**，不是漂移；
* 方案 §3.3 的边界条件"ω≈0 时窗口内角度覆盖不足"正是这件事的物理原因：
  覆盖不足 ⇒ 代价函数在 yaw 方向上是平谷 ⇒ 拟合出来的 yaw 不可信，**即使 rmse 看起来不大**。
  所以更稳的门是**相位跨度**（弧段端点之间的 Δθ = |ω|·T），而不是只看 rmse。

**动作**：把 yaw 注入的门从 `max_rmse_deg = 0.4°`（16.7 px）收到 **3 px** 量级，
或者按 `Δθ ≥ 30~40°` 门控；ω 通道可以继续用宽松门（ω 的稳健性远好于 yaw）。

### 2.3 跨板联合的相位不是固定 π/2

四块板的相对相位是 `k·π/2`（k ∈ {0,1,2,3}），而且换板时 k 要**估**出来。
UV 的实现用"种子帧 PnP 板心相对 C 的方位角"定 k，比固定 π/2 稳（避开病态 yaw）；
另外本轮实测：**跨板窗口本质非凸**——合成自检 S2（前半板 A、后半板 B、θ 连续）
有时精确收敛（0.9 px、ω=2.92），有时落进坏解（34 px、ω=5.24）。
所以跨板联合必须保留"失败就退化为单板"的回退（UV 已有，`tracker_localfit.cpp:263`）。

### 2.4 命中率增益的说法要降级

方案 §2/§7/§10 的 "+12%~+15%" 是从更早的 A/B 抄来的。按本轮证据，拟合器**可证**的增益是：
中速 + 正面时的 **ω** 与**旋转中心**；yaw 只在好拟合上可用。
而 2–4 rad/s 区间"单帧 PnP + EKF 本来就够用"（sp_vision 报告 §7.4 的可观测性分析），
5 rad/s 以上主流方案不跟板。建议把这行改成"**待验证**"，验收口径直接用
`docs/layer_error_budget.md` 里现成的量（`aim_settled` 占空、`|yaw_err|`、`in_fire_window`）。

### 2.5 `tag_id` ≠ 板号

`tag_id`（本项目是 NN 的 `number` 类）回答的是"**这是哪台车**"，不是"**这是车上的第几块板**"。
板号 0..3 只能由几何给出（相对车心的方位角 + EKF 关联）。
方案 §5.1 写"直接识别装甲板数字 → 板编号"会把这两件事混在一起；
`ArmorIdRecognizer` 的正确定义应该是：**输入 = PnP 径向角 + EKF 关联结果（马氏距离）+
历史投票，输出 = 板号 0..3**，多帧投票只用于抑制抖动。

### 2.6 EKF 相位转换不要加

方案 §4.7 的 `θ_sel = θ_ref + π/2·(id_sel − id_ref)` 是针对"拟合器 yaw 带板号偏移"的写法。
本项目在 2026-10-11 的审计（`docs/local_fit_tracker_responsibility_audit.md` P1-2）里
**已经把拟合器的相位表改成与 EKF 同一张表**，`LocalFitResult::yaw` 现在就是**底盘 yaw**，
注入用 `kChassisYawPlateId = 1`（0° 板）。再叠一次相位偏移会**双重计数**，
等于把 yaw 观测拧 90° 的整数倍。

### 2.7 2D 优化（钉死 ψ 与 t_z）——**已实现并测过，结论是不要做**

已落地：`estimation/pose_2d_solver.{hpp,cpp}`（在 ψ、t_z 固定时**严格线性**，
闭式一次解出 t_x,t_y；放开 t_z 时几轮 GN）+ `test/pose_2d_solver_test.cpp`（ctest 已接入）。
它同时验证了方案里**对**的部分和**错**的部分：

| 量 | 6D PnP（IPPE，σ_px=0.5px、2.2 m、132 mm 板） | 2D 求解器 | 判定 |
|---|---|---|---|
| 正面 yaw | 1.40° | 继承输入的 **0.57°**（实车好拟合实测） | **拟合器赢 2.5×** ✓ |
| (t_x,t_y) | **0.27 mm** | 0.26 mm（真值 ψ,t_z）／0.27 mm（实测 σ_ψ=0.6°、σ_Z=2cm） | **没有增益** ✗ |
| t_z | **5.8 mm** | 不估计（按输入固定）；方案说拟合器 Z 是 10~50 mm | 钉成拟合器的 Z → **变差 2~9×** ✗ |

**结论**：(t_x,t_y) 与 t_z 本来就由角点决定、已经在噪声底
（σ_tx ≈ σ_px·Z/fx ≈ 0.46 mm，实测 0.27 mm），"降维"买不到它们；
能买到的只有 **yaw**——也就是角点看不见的那个方向。
而 UV 现有的 `refineArmorYaw()`（固定 tvec + 1D ψ 搜索）**已经就是正确的分解**；
把 t_z 也钉给拟合器是往反方向走。

两个副产物（都在单测里钉住了）：

* **机械倾角有数值证据**：正面观测时 ψ 的 profile-cost 曲率 pitch=0° → 10.75、
  15° → 582.5（**54×**）——直接验证方案 §2.1/§8.3 的机制。
* **灵敏度**：ψ 偏 1° 只让 (t_x,t_y) 动 **0.03 mm**（残差 0 → 0.11 px），偏 5° 动 0.17 mm。
  即 ψ 的误差**不污染位置**，只污染**朝向**并在残差上留痕 —— 这正好给了一个廉价的门控：
  用 2D 残差反查"这一帧的 ψ 可信不可信"，比只看拟合 rmse 更直接。

## 6. 追击：为什么 UV 的"可用拟合率"只有 0.6%（2026-10-12 下半场）

起点是上一轮的交付数字：同一份 `det2.csv`，**UV 的拟合器"rmse≤3px"只占 0.6%（2/343）**，
而 sp 端口同一套算法同一份数据能到 **18%**。差 30 倍，必须查清。

### 6.1 先排除的嫌疑（都不是）

| 嫌疑 | 结论 |
|---|---|
| 回放 harness 与真机口径不一致 | **不是**。回放每帧设 `use_rcv=true` + `rcv=tracker.fitterRcv()` + `h_prior=chassisGeometry().height(0)`，与 `real_runner` 同口径（`tools/replay_obs_csv.cpp:486-494`） |
| 端点没去畸变 | **不是**。`pushArmorLightBars` 内做 `undistortPoints`；靶在画面中心附近，畸变影响 <0.1px |
| `h_prior` 给错（会把残差顶到几十 px） | **不是**。底盘几何的 `height(0)=0` |
| 模型参数不在位 | **不是**。α=15°、L=0.06、W=0.135 都按配置生效 |

### 6.2 两个关键实测

**① 残差分布是多峰带断崖**（343 次拟合）：

```
[0,2)=0   [2,3)=2   [3,4)=72   [4,6)=14   [6,8)=1   [8,10)=0   [10,12)=50   [12,16)=27   [16,20)=165
```

`[3,4)` 挤了 72 个、`[8,10)` 一个都没有 —— 这种形状说明结果由**"落哪个盆地"**决定，
不是一条连续的系统偏差。

**② 单参数扫描是刀刃式的**：

| 参数 | 扫描结果（拟合 rmse ≤3px 的占比） |
|---|---|
| `lightbar_len` L | 0.050→0% ｜ 0.055→0% ｜ 0.058→0% ｜ **0.060→0.6%** ｜ **0.065→16.9%** ｜ 0.070→0% ｜ 0.075→0% ｜ 0.080→0% |
| 安装倾角 α | −15°→0% ｜ **0°→23.9%** ｜ 10°→21.0% ｜ **15°→0.6%** ｜ 20°→0% |

连续参数把可用率从 17% 打到 0%，**这不是物理，是盆地抽签**。所以"用 rmse 去扫 L/α"是
无效的（而且 α=0 的"好"很可能是**平谷伪好**：yaw 不可辨识时残差自然小——正是 15° 支架
要解决的那个病态）。

### 6.3 起点盲扫也不是原因

给拟合器喂"EKF 当前 yaw + ω"当第一个起点（等于把 16 个盲扫起点的第 1 个换成状态先验），
343 次拟合的 rmse **逐位不变**（0.6% / p50 16.33）——那个起点根本不会胜出。
所以**不是起点覆盖不足，而是代价函数本身存在一个 ~16px 的吸引域**
（16px @1.4m ≈ 9mm 的 3D 模型误差）。该改动已回退，不留无效开关。

### 6.4 顺带证实的一条

UV 现在把**本帧全部检测**都推进拟合缓冲，sp 端口只推**关联到的那一块**：
p50 从 16.3 → **12.8px**（与端口的 11~12px 吻合），但 ≤3px 仍是 0.6%
→ 多板混弧影响的是**典型值**，不解释可用率。

### 6.5 结论与下一步

30 倍的差**不在 harness、不在起点、不在某个单参数**，而在**模型几何常数与检测关键点
之间的匹配**：同一套算法、同一份数据、只有几个常数不同就能差 30 倍，说明这些常数根本
没标定到"这套检测关键点"上。

所以正确的做法不是继续扫：**把 (L, W, α, R_cv 家族成员, 单板推入策略) 当联合待标定量，
目标函数直接用"≤3px 占比"或中位 rmse**（而不是拿 rmse 当单项指标逐参数调）。
端口那组组合（W=0.1315、L=0.060、`R_cv=(R_g2w·R_c2g)ᵀ·B`、只推关联板）已经是一个
**18% 的可行解**，可以当作标定的起点。

**在这之前，建议维持"拟合器注入关闭/无害"**：现配置（`use_fit_radius: false` + yaw/ω
质量门）已经把它从"确定性有害"变成中性，但没有收益。

### 6.6 新增的两个诊断开关（env，只影响诊断不改行为）

| 开关 | 作用 |
|---|---|
| `ULTRA_VISION_LOCAL_FIT_DIAG=1` | 每 200 帧打印喂给拟合器的前提：`h_prior / α / W / L / 本帧推入板数 / use_rcv / Rgeo` |
| `SPV_PUSH_FIRST=1` | 只把本帧第一块检测推入（= sp 端口口径），用来 A/B"多板混弧"的影响 |

## 7. 根因与修复：板宽被硬编码架空（2026-10-12 收尾）

### 7.1 根因

`Tracker::pushArmorLightBars` 里写的是

```cpp
constexpr double k_local_fit_plate_width = 0.135;   // ← 硬编码
push_bar(armor.left,  +0.5 * k_local_fit_plate_width);
push_bar(armor.right, -0.5 * k_local_fit_plate_width);
```

而**检测关键点/PnP 用的是 0.1315**（`configs/tracker.yaml` 的 pnp 段与 camera.yaml 同源）。
也就是说：拟合器 yaml 里的 `plate_width` **从来没生效过**，实际喂进去的一直是 0.135 ——
2.6% 的切向间距误差，在 1.4m 处折合每根灯条 ~3px 的系统偏移，
正好是残差直方图里那一簇 `[3,4)=72`。

### 7.2 修复后的实测（det2.csv，343 次拟合）

| 配置 | ≤3px | p10 | p25 | p50 |
|---|---|---|---|---|
| 修复前（有效 W=0.135，硬编码） | **0.6%** | 3.21 | 4.23 | 16.33 |
| **修复后（有效 W=0.1315，走 yaml）** | **16.3%** | **2.84** | **3.96** | 16.44 |
| 修复后 + 每帧只推一块板（sp 端口口径） | 16.3% | 2.84 | 3.96 | **12.80** |
| sp 端口（同一份数据，参照） | ~18% | ~2.9 | — | ~11.2 |

**可用率 0.6% → 16.3%（27 倍）**，与端口基本追平。

代码改动：`plate_width` / `lightbar_len` 现在由 `tracker.local_fit` 给
（`LocalFitConfig` 新增两个字段，A 段门控与 push 共用同一份），yaml 显式写 0.1315/0.060。

### 7.3 仍然刀刃式的那个量：L

| L（灯条长） | ≤3px |
|---|---|
| 0.055 | 0% |
| **0.060** | **16.3%** |
| 0.065 | 0% |

连续参数把可用率打到 0 —— 说明 **L 只能当"标定常数"锚定在板高上（0.060），不能拿 rmse 去扫**。

### 7.4 系统级：这一轮**还没换来收益**

底盘一致性指标（检测↔模型板心中位）：

| 配置 | 中位 |
|---|---|
| 拟合器关（基线） | 33.91 px |
| 修复后 + 质量门（注入关闭/无害） | 33.93 px |

几乎没有差别。原因是这条指标在这份录制上**被另一件事主导**：
状态行里 `Rgeo=0.3296/0.1704` —— **几何慢层已经漂成 ±8cm 的不对称四边形**
（`geometry_learn` 的老问题，见 `docs/spv_port.md`），而 sp 端口**根本没有几何学习**、
所以它是 3.4px。

**结论：修复拟合器的下一张多米诺是几何慢层，不是拟合器本身。**
顺序应该是：① 把 `geometry_learn` 关掉或加硬约束（用同一份数据 A/B 验证指标回到十几 px 以内）
→ ② 再回来看拟合器已经可用的 16.3% 拟合能带来多少（那时才有干净的背景）。

## 8. 底盘模型 10 倍差距的追击（2026-10-12 最后一轮）

### 8.1 `geometry_learn` 假设被数据否掉

原以为几何慢层漂到 `Rgeo=0.33/0.17` 是元凶，实测**相反**：

| 配置（拟合器关） | 检测↔模型板心中位 |
|---|---|
| `geometry_learn=true`（现状） | **33.91 px** |
| `geometry_learn=false` | 42.35 px |

`geometry_learn` 是在**帮忙**（它把逐板距离往观测上拉），不是害人。假设作废。

### 8.2 同帧对齐：10 倍差距是真的，不是统计口径

用两个工具各自 `--out` 逐帧落盘再按时间戳对齐（1380 帧全对齐）：

| 子集 | spv 中位 | UV 中位 |
|---|---|---|
| 全部共同帧 | **2.76 px** | **48.75 px** |
| spv 敢锁的 823 帧 | 2.19 px | 25.96 px |
| spv 放弃的 205 帧 | — | 70.82 px |

所以"spv 只统计好帧"这个解释**不成立**——同一帧上 UV 就是差 10~20 倍。

### 8.3 找到并修掉一个配置级根因：`distance_noise_scale`

`tracker.hpp` 的注释里写着"sp_vision 的 `distance_noise_scale=1.0`（σ≈1m，基本不信
PnP 深度）……我们的实车深度噪声 ±12cm"，但 **yaml 里填的是 0.0**（按**仿真**定的：
仿真深度几乎无噪，降权只会丢信息）。实车数据实测：

| `distance_noise_scale` | 检测↔模型板心中位 | 旋转中心深度 cz 中位 |
|---|---|---|
| 0.0（原配置） | **33.91 px** | 1.53 m |
| 0.5 | 24.41 px | 1.43 m |
| **1.0（已改为这个）** | **22.88 px** | **1.36 m** |
| 3.0 | 22.31 px | 1.31 m |

即"降权 PnP 深度"在实车上有用 —— 与注释里的物理判断一致，只是值当初被仿真结果带偏了。
**单这一项就把主指标改善 32%**（33.91 → 22.88）。已改 yaml 并写清依据。
⚠ 这个键必须仿真/实车两边都判（`truth_regression_selftest` 只自检度量代码本身，
**不覆盖**仿真精度回归），所以仿真侧还需要单独确认一次。

### 8.4 仍然存在的 8 倍差距（下一个要查的）

对齐同帧的状态对比揭示两者**估的不是同一个目标状态**：

| 量 | spv | UV |
|---|---|---|
| 旋转中心到相机距离（中位） | 1.249 m | 1.533 m |
| yaw 差（模 90°，中位 / std） | −10.2° / 24.7° | — |
| `getOmega()`（**UV 是独立的 rotation_rate 估计器**，不是 EKF 的 ω） | EKF ω ≈ 0.001 | 3.52 rad/s（58% 帧 \|ω\|>1） |

⚠ 最后一行**不是同一种量**（UV 的 `--out` 里 `omega` 列来自 `tracker.getOmega()`＝
rotation_rate 估计器；spv 的来自其 EKF 的 w），所以不能直接读成"UV 幻觉自旋"。
把 UV 的 EKF yaw 逐帧差分得到的速率是**中位 0.000、>1rad/s 占 0%**（spv 44%），
但这个 `ekf_yaw_deg` 列本身可疑（冻在 0.000 不像真实行为），**下一步要先确认这一列
的来源**，再决定是"估计器不更新"还是"度量列写错"。

**下一步清单**（按性价比）：
1. 确认 `--out` 的 `ekf_yaw_deg` 列来源，然后比较两边的 **EKF 状态**（不是各自模块的输出）；
2. 比较两边的**观测函数**（UV 的 YPD+armor-yaw+IESEKF vs spv 的单次线性化），看是同一组观测被解释成了不同的状态；
3. 仿真侧复核 `distance_noise_scale=1.0`。

## 9. 第 1 步做完：诊断列修好，但**指标本身不可信**（2026-10-12 收尾）

### 9.1 先修诊断列（`--out` 的 `ekf_yaw_deg` 恒为 0 是写错了）

原写法：

```cpp
out << (have_fit ? tracker.getYaw() * 180/M_PI : 0.0);   // ← EKF yaw 被 have_fit 门控
```

拟合器一关（`have_fit=false`），整列恒 0 → 读起来像"EKF yaw 冻住"。**那是诊断列的锅，
不是估计器的行为**（上一轮据此得出的"EKF 不更新"结论已作废）。已改成：EKF 的 yaw / ω
任何时候都写（拟合器的量没有才写 0），并补上 `ekf_omega` 列。

### 9.2 修好后：幻觉自旋是真的，而且它**在替真问题打掩护**

用修好的列比较同帧状态：

| 量（同帧） | spv | UV |
|---|---|---|
| EKF ω 中位 | **+0.000** | **+3.517** |
| \|ω\|>1 的帧占比 | 2% | 58% |

ω 的过程噪声来自 yaml 的 `process_noise_vel`（映射到 `ekf_cfg.process_omega`）。扫描：

| `process_noise_vel` | EKF ω 中位 | \|ω\|>1 | **检测↔模型板心中位** |
|---|---|---|---|
| **400（yaml 现值）** | **+3.517** | 58% | **22.9 px** |
| 1.0 | −0.013 | 0% | **119.2 px** |
| 0.2 | −0.001 | 0% | 91.3 px |
| 0.05 | −0.003 | 0% | 91.1 px |

把 ω 压到与 spv 一致的 ≈0（即"不再幻觉自旋"）之后，UV 的模型离观测有 **90~120 px**。

### 9.3 结论：**"检测↔模型板心"这个指标在模型自旋时会系统性偏乐观**

模型自己在扫圈时，"每块检测到最近的模型板心"总会**偶尔**扫中，中位因此被拉低；
模型稳住不动、但 yaw/中心本身错了时，误差是一个**恒定的 90~120px**。
所以之前所有用它做的 A/B（33.9 / 22.9 / 3.4px）都需要重新审视：
**它奖励"会扫圈的模型"**，这正是 UV 那 3.5 rad/s 的用武之地。

（spv 不受影响：它 ω≈0 且指标 2.76px —— 说明它的模型是真的贴在观测上。）

### 9.4 下一步（口径要先修）

1. **换度量**：不要用"检测↔最近模型板心"，改成
   **"预测板心 ↔ 同一板号的检测板心"**（按板号配对，而不是取最近），
   或者干脆用"重投影四角点 vs 检测四角点"。
2. 换完度量后再比较 spv / UV，才能知道 UV 的模型到底差多少（现在只知道 ≥90px）。
3. 然后才谈"为什么 UV 的 yaw/中心错了"（观测函数 / 关联 / 重锚）。
