## 1. 运行时拓扑

```

│  JPEG q95 + 32B 头      │ ─────────► │  │ 帧接收线程 VisionDateReceiver      │  │
│                         │            │  │  (解码 JPEG → 最新帧 + 条件变量)   │  │
│  指令: GIMBAL/FIRE/RESET│ ◄───────── │  └────────────────────────────────────┘  │
│        7667 TCP         │            │  ┌────────────────────────────────────┐  │

│                         │ ─────────► │  └────────────────────────────────────┘  │
└─────────────────────────┘            │  ┌────────────────────────────────────┐  │
                                       │  │ 云台线程 GimbalController 100 Hz   │  │
                                       │  │  （加加速度受限轨迹 + 前馈）        │  │
                                       │  └────────────────────────────────────┘  │
                                       │  ┌────────────────────────────────────┐  │
                                       │  │ 主线程（视觉主循环，~20-24 fps）    │  │
                                       │  │  取帧 → 检测 → PnP → EKF → 瞄准    │  │

                                       │  └────────────────────────────────────┘  │
                                       └──────────────────────────────────────────┘
```

- 仿真侧：`rune_only` 模式默认 **30 fps**、JPEG q95（`tcp.rs:324,238`）。
- 视觉侧：4 个线程（帧接收、指令下发、遥测、主循环），主循环与其余线程通过最新帧/队列解耦。
- 主循环实测 **p50 41 ms/帧 ≈ 20~24 fps**（瓶颈是 OpenVINO 单帧推理），即**仿真给的帧我们丢掉了 1/3 以上**。

## 2. 数据流与"谁决定什么"

| 级 | 代码 | 输入 → 输出 | 备注 |
|---|---|---|---|
| 解码 | `rune_model.cpp` | 640x480 BGR → 候选（5 点 + 3 类分） | 归一化 0~1；中心距 NMS 30 px |
| 选靶 | `rune_detector.cpp` | 候选 → 一个扇叶（靶心/R 标） | 亮点判据 + 锁定滞回 + `require_inactive_class` 过滤 |
| 解算 | `rune_solver.cpp` | 4 点 → 位姿（rvec/tvec） | IPPE 双解按"圆心反投影落在 R 标"选；深度用 `focal*0.7/像素偏移` 校正 |
| 估计 | `rune_target.cpp` | 观测 → 状态 | 7/10 维 EKF；相位 = 几何相位（新） |
| 瞄准 | `rune_aimer.cpp` | 状态 → yaw/pitch + 开火许可 | 两遍弹道解 + 瞄准角滤波；`fire_gap` 节流 |
| 激活 | `rune_activation.cpp` | 图像相位 + 命中反馈 → 窗口/开火许可 | `gate_fire` 默认关 |
| 指令 | `gimbal_controller.cpp` | 目标角 → 100 Hz 轨迹 → TCP | 视觉只更新目标角 |

**"打哪一片、能不能打"的判定散落在 4 处**：检测器（锁定/亮度/类别）、节点（`aim_phase` + 激活窗口 + `post_hit_hold` + 类别闸门）、瞄准器（换叶判定 + 开火节流）、解算器（相位隐含在 PnP 选解里）。

## 3. 时间基准与延迟预算（实测）

- 视觉得到的帧带两个时间：仿真**曝光时间**（`source_timestamp_us`，当前**没有使用**）和本地**到达时间**（`frame_local_timestamp_us`）。
- 解算用的相机姿态取"到达时刻"的指令快照（`gimbal_controller.snapshotAt(frame_local_timestamp_us)`）——**不是曝光时刻**。
- 瞄准的提前量：`detection_age = now - timestamp`，而 `now` 在**推理之前**采样 → **不含 41 ms 推理时间**，也不含传输时间。
- 结论：瞄准存在 **~40~70 ms 系统性欠补偿**；小符 60°/s → 2.4~4.2° 相位（≈0.3~0.5 m 横向），大符 120°/s → 翻倍。

## 4. 参数分布（物理量 / 经验值 / 域假设 混在一起）

| 类别 | 例子 | 说明 |
|---|---|---|
| 物理量 | `target_radius_m`、`bullet_speed`、相机内参 | 可标定、可解释 |
| 模型约定 | `input_scale`、`plate_point_order` | 换模型必须重标（有实测方法） |
| 经验/试出来的 | `score_threshold`、`lock_break_px`、`fire_gap_time`、`min_plate_radius_px` | 证据强度不一，需按曲线复核 |
| 域假设 | `require_inactive_class`、亮点判据窗口、`hub_brightness_margin` | 仿真美术与实车不一致时行为不同 |

## 5. 系统设计缺陷清单（排查用）

### 架构级

| # | 缺陷 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| A1 | 感知链路全串行，帧率被网络推理锁定 | 主循环 p50 41 ms；仿真 30 fps 而我们 20~24 fps | 丢帧 1/3；推理抖动直接变成控制抖动 | 推理异步化（独立线程/流水线），主循环只做"取最新结果" |
| A2 | 几何只有单帧，没有时间维度 | 观测距离逐帧 5.8~7.7 m（真值 6.05）；参考实现用平面窗口 SVD | 圆心/距离/法向抖动直接进瞄准 | 加世界系平面/圆心滑动窗口（参考 `PowerRunePlane`） |
| A3 | 决策点分散（4 处） | 见 §2；`post_hit_hold`/`gate_fire`/类别闸门/换叶判定各管一段 | 行为难推理、拍板只能靠试参数 | 收敛成单一"目标与开火状态机"（输入：观测 + 类别 + 遥测） |
| A4 | 缺少失目标保底行为 | 无目标帧里 238/323 帧网络最高分=0（符不在画面）；且滑行时按 60°/s 外推会把相机甩出 40°+ 再归位 | 盲目期长、且会主动把符甩出视野 | **已修**：`observation_life_s=0.2` 后改用 `aimCenter()` 瞄圆心 + 滑行时清零圆心角速度 `x[1]`；实测甩飞指标 5 次/47.8° → **0 次/5.5°**（见 `docs/energy_rune_vs_rp26.md` §8 第 4 步） |
| A5 | 开火没有"命中时刻"概念 | 固定 `fire_gap` + 布尔闸门；实测 48% 的弹在本轮失败后落地 | 弹浪费、命中率低 | 解算拦截时刻 + 短连发窗口（参考弹道模型 + 火控节流） |

### 实现级

| # | 缺陷 | 证据 | 影响 |
|---|---|---|---|
| B1 | 时间基准不一致（A1/A4 的同源问题） | 姿态快照用到达时间；`detection_age` 不含推理；`telemetryField("t")` 曾命中 `event=` | 系统性欠补偿 40~70 ms；日志时间无法对齐（已修） |
| B2 | 单线程里做 I/O（CSV、`imwrite`、可选 `imshow`） | 主循环尾部 | 帧时间抖动（录制时更明显） |
| B3 | 容器/内存没有复用约定 | `cv::Mat` 每次 clone、JPEG 解码每帧新分配 | 帧率与抖动 |
| B4 | 数值防护靠散落判断 | 例如 PnP 选解、`min/max_distance_m`、hint 合理性区间 | 行为不易回归测试 |

### 工程级

| # | 缺陷 | 证据 | 影响 |
|---|---|---|---|
| C1 | 没有运行时自检 | 只有 CSV/摘要；没有"瞄的那片是不是亮点"这类断言 | 故障要事后翻日志才发现 |
| C2 | 观测数据没有统一时间轴 | 今天才补 `sim_t` | 曲线无法与轮次对齐 → 容易得出错误结论（我上一轮就踩了） |

## 6. 昨天那段录屏（基线）说明"架构本身是够用的"

录屏（文件时间 09-22 19:47，早于本次所有改动）是一个**成功案例**，量化结果
（红色=已激活图案，面积随激活片数阶梯上升）：

```
t=0.5s  1284 px   （1 片刚点亮）
t=2~8s  3164→8428 px  逐步 +1650 px/次 ≈ 每命中一次点亮一片
t=9.5s  0 px     机关复位（5 片满 → 保持 → 复位）
t=11~21s 1452→15432 px 第二轮继续增长到 4~5 片
```

注意：HUD 上的 `hit=` 是**步兵装甲板**命中数（`main.rs:133` → `armor_hit_count()`，只在 `ArmorHitbox` 命中时增加），**与能量机关无关**；看它判断"符打没打中"会得出完全相反的结论。

结论：**架构能跑通 5 连击（录屏为证），当前新模型的差距在感知/节奏，不在架构骨架**；
但 A1~A5 这些缺陷在旧模型（关键点更干净）下被掩盖了，换成新模型后全部暴露出来。

顺带两个从帧里确认的**外观语义**（用来校验类别）：
- **靶心（同心环）= 未激活 = 该打的那片**（模型应给 class 0）；
- **"箭头/圆环+横条"= 已激活 = 打过的那片**（模型应给 class 1/2）。
  t=8 s 那帧正是"4 片已激活 + 1 片靶心"，说明一轮 5 片、每命中一次变一片。
