# auto_aim 瞄准闭环：口径、实测、当前结论

2026-09-26。配套工具 `tools/auto_aim_aim_check.py`，配套工况开关
`tools/auto_aim_sim_test.sh --distance/--pan/--pan-lead/--gyro`。

## 1. 仿真里的瞄准闭环长什么样

`simulator/src/main.rs::remote_camera_gimbal` 会把**我们下发的云台指令**直接
变成**主相机的位姿**：

```
camera_rotation = home_rotation · R_y(-cmd_yaw) · R_x(cmd_pitch)
```

所以 `truth.csv`（板子在**当前相机系**里的位置）本身就是一个闭环量。实测符号
关系（给仿真发一条指令，等 0.4 s 再看真值）：

| 下发指令 | 靶面 apparent yaw | 靶面 apparent pitch |
|---|---|---|
| `GIMBAL 0 0` | -0.02° | +0.28° |
| `GIMBAL +5° 0` | **-5.02°** | +0.28° |
| `GIMBAL 0 +5°` | -0.02° | **-4.72°** |

即 `apparent = 基线 - cmd`。这和视觉端的模型是自洽的：视觉端算的是
"当前指令角 + 相机系里的目标角"= 绝对指令角，所以闭环一步收敛而不是正反馈
（这一点必须实测确认过，符号反了会变成云台一路跑飞）。

## 2. 对账时必须把真值转回 home 系

selector.csv 的 `target_yaw/target_pitch` 是 **home 系（云台零位系）角度**，
而 truth.csv 是**相机系**位置。所以：

```
yaw_home   = atan2(x, z)      + cmd_yaw
pitch_home = atan2(-y, hypot(x,z)) + cmd_pitch
```

`cmd_yaw/cmd_pitch` 取同一时刻的 `observation.csv`（它就是视觉端用来反旋观测的
那一组角）。**别直接用相机系角度比 target_yaw**，差一个 cmd 量级。

还有一项是"故意"的偏差：selector 瞄的是**抬了 0.5·g·t_fly² 的瞄准点**，
6.5 m / 25 m/s 时 ≈ 3.1~3.5°（0.47 m）。工具默认扣掉（`--no-ballistic` 可看原始值）。

## 3. 指标定义

* `pred`：selector 在 t 时刻给出的 (t+lead) 预测角 vs **真值在 t+lead 时刻**
  最近板的 home 系角；取最近板是因为四板相隔 90°，1~2° 误差不可能认错。
* `横向误差`：`Δyaw × 距离`（cm）。距离用真值，不用估计。
* `提前量欠量`：把误差投影到**真值该板的 home 系角速度**方向：
  `-(Δyaw·ω_yaw + Δpitch·ω_pitch)/|ω|²`。正数 = 瞄点在靶后面。
  注意必须用 **home 系**角速度：相机系角速度里混着"云台自己转"的成分
  （实测能到 20~50 deg/s，比靶的运动大一个量级）。
* `指向偏置(⊥)`：扣掉提前量分量后剩下的部分，是真正的静态指向误差
  （滤波器再怎么调也改不了，得查 PnP/标定/中心定义）。

## 4. 本轮实测（6.5 m，1440x1080，仿真）

工况：`--pan 0.8` = ±2 m 来回 @0.8 m/s，段与段之间速度是**阶跃**的
（等价于实车按 WASD/R 键那种"瞬时给速度"，也正是"跟不上平移"最刺眼的地方）。

| process_noise_pos | 横向误差 中位 | p10 / p90 | 平移段欠量 中位 | 近距 1 m FIRING |
|---|---|---|---|---|
| 1（原值） | +0.3 cm | −18.9 / +24.3 | +48 ms | 81 / 115 / 82 |
| 10（常数） | +0.1 cm | −9.6 / +10.0 | +17 ms | **16 / 15 / 17** ← 回归 |
| 30（常数） | +0.9 cm | −9.0 / +9.1 | +24 ms | 未测 |
| 100（常数） | — | 决策占空 85%→36% | — | — |
| **自适应（现值）** | −0.1 / +0.3 cm | −13.8 / +11.2 | +59 / +80 ms | 104 / 113 |

结论：**常数调大能治平移，但会把近距静态工况打死**——过程噪声的物理含义是
"底盘加速度的不确定度"，静止时本来就该是 0。所以改成按速度自适应：

```
qa = clamp(process_noise_pos · (1 + (|v|/speed_ref)²), ·, process_noise_pos_max)
speed_ref = 0.28 m/s, max = 40       # |v|=0.8 m/s → qa≈9.2，≈实测最优的常数 10
```

旋转靶（`--gyro 1`，2.4 rad/s）对这三个值都不敏感：横向 p10/p90 都在 −8/+7 cm，
欠量 −26→−2 ms，FIRING 94/110/102 → 自适应 93，**没有回归**。

## 5. 仿真环境本身的两个坑（会污染测量）

1. **`DAEDALUS_MOVE_LOOP` 原来完全不生效**，三处 bug：
   `scheduled_vehicle_input` 挂在 `remote_vehicle_controls` 里，而那个系统要
   `Single<(&mut Transform, &mut InfantryChassis), ...>`，`armor_chassis` 场景的
   靶车（`spawn_vehicle_scene`）**没有** `InfantryChassis` 子节点 → `Single` 匹配
   0 个实体 → 整个系统被 Bevy 跳过（日志里一行 `[move]` 都没有）；
   段时长被当成绝对时刻用；段表还被按第一列排了序。已修，并改成独立的
   `scripted_vehicle_motion`（只依赖 `InfantryRoot`），用 `MainCameraHome`
   作参考系（用当前相机位姿的话，运动方向会跟着云台转，靶车绕着相机画圈）。
2. **靶车在仿真里会被"推着走"**：不加任何脚本运动时，6.5 m/1 m 工况下中心
   仍会自己漂 0.3~1.9 m（子弹命中冲量 + 自身沉降/与本地机器人碰撞都可能是来源）。
   所以"静止工况"并不静止，比 q 值更小的影响都会被它淹掉。下一步应该把
   `armor_chassis` 场景的靶车锁成完全不动（或让弹丸不与靶车碰撞）。

## 6. 还没解决：锁定（acquire）很脆

现象（`--pan 0.8 --gyro 1`）：首帧同时看到 4 块板时，跟踪器**永远锁不上**
（`observation.csv` 0 行、`lost` 一路涨），而 selector 里那条冻结的估计
（真值 6.5 m，估计出来的"板"在 1~2 m）会把云台一路带到 80~90° 出画，
整轮再也回不来。同一工况重跑 3 次都是"首帧 armors=2 → 正常锁定（344/346/343 行观测）"。
最早那轮 3 s 前导静止的 pan 工况也是这个死法（14 条决策、云台转到 86°）。

这和用户报的"识别不到"是同一件事：**不是距离问题，是锁定期的脆弱 + 云台会追着
假目标跑**。下一步优先级：

1. 云台指令加"确认"闸门：`TEMP_LOST`/刚重捕/估计跳变超过阈值时**保持**而不是跟；
2. 首帧多板时先做几何一致性（四板半径 0.21 m、角度互差 90°），别让单块假板定生死；
3. 给估计的距离加"和靶面像素尺度一致"的硬闸门（1~2 m 的假解在这个闸门下会直接被拒）。

## 7. 收敛看门狗（2026-09-29）

参考：`sp_vision_25/tasks/auto_aim/tracker.cpp`（发散与 NIS 失败比例判定、`dt>0.1s → lost`）
与 `tasks/auto_aim/target.cpp::diverged()/convergened()`。sp_vision 没有"目标转不转"的
差别，它靠的就是这两条 + 帧间隔判据；Ultra_Vision 的差别只在状态量（我们没有
`r`/`dz` 两个状态），所以判据二换成了速度 / 角速度 / 位置模长 / 位置协方差四个上限。

代码：`src/auto_aim/Kalman/tracker.{hpp,cpp}`（`noteMeasurement / watchdogTrip /
stateDiverged / watchdogStats`），参数在 `configs/tracker.yaml` 的 `watchdog_*`。

判据与动作：

| 判据 | 触发条件 | 对应 sp_vision |
| --- | --- | --- |
| 一 · 量测长期被拒 | 最近 `window` 帧（只数有观测的帧，含"有框但关联不上"）内被拒比例 ≥ `reject_ratio`，且样本 ≥ `min_samples` | `recent_nis_failures ≥ 0.4·window_size` |
| 二 · 状态发散 | `|v|>12 m/s` 或 `|ω|>20 rad/s` 或 `|center|>30 m` 或位置方差 > 25 m² | `Target::diverged()`（r/l 越界） |
| 三 · 帧间隔过长 | 非 LOST 且两帧间隔 > `max_frame_gap`（0.2 s） | `dt > 0.1s → lost` |

命中任一 → `state = LOST` + `force_reinit_`，下一帧**跳过** `tryReacquire`、直接用观测
`init()`；`LOST` 会让 `AimPipeline::track_usable = false`，即只发心跳（mode=0）
不再给云台下目标，避免"追着假目标跑/大角度摆"。

实测（`~/real_full`，静止单板，1400 帧，`build/replay_dataset`）：

| 工况 | 整段最大拒绝比例 | 触发重初始化 | 估计 vs 观测 | 重投影 |
| --- | --- | --- | --- | --- |
| 默认参数 | 0.00 | 0 次 | 0.18 mm | 5.4 px |
| 故意把 `reject_ratio` 压到 0.05（灵敏度探针） | 0.00 | 0 次 | 0.14 mm | 5.4 px |
| 故意把 `ypd_nis_threshold` 压到 0.5（破坏量测通道） | 0.75（第 511 帧） | 1 次 | 0.13 mm | 5.3 px |

结论：干净数据上余量极大（门限 0.4 vs 实际 0.0，连 0.05 都碰不到），量测通道真的
系统性不自洽时会命中并按预期重初始化，而且重初始化后精度不掉。
单元测试（`src/auto_aim/test/armor_ekf_test.cpp`）把三条判据、无误差不误触发、以及
"命中 → 重新初始化 → 3 帧后重新报已收敛且不再重复触发"整个闭环都钉住了。

**已知边界**：打开 `hard_plate_constraint` 后底盘中心被观测板强行锚定，于是
`center` 与 `radius` 沿视线方向可以互相抵消 —— 看门狗和 EKF 都**看不到"半径选错"**
这件事。实测（同一段 `~/real_full`，`armor_radius` 0.21 → 0.5，即偏了 0.29 m）：
整段最大拒绝比例**仍然是 0**、触发 0 次，而"估计 vs 观测"和重投影都只统计**被观测
的那块板**，所以照样好看（0.31 mm / 5.4 px）—— 这个指标本身看不见外推板。
按几何算（四块板绕中心 90° 均布，相邻板方向差 90° → 位移 = √2·Δr）：
另外三块外推板会整体偏 **√2×0.29 ≈ 0.41 m**。
所以"外推的 3 块板对不上"是整车建模问题（`r` 该进状态量、或按真车量准），不是收敛问题。

补一条 sp_vision 的做法（`tasks/auto_aim/target.cpp` 的 Q 矩阵第 8/9 行全是 0，
`tracker.cpp::set_target` 里 `Target(armor, t, 0.2/0.2765/0.3205, ...)`）：他们
**把半径当常量**（Q_r = 0，不自由发散），只在初始化时按兵种给一个实测值，再把
`convergened()/diverged()` 当"可信度闸门"。也就是说"目标转不转"确实不是他们的分岔点 ——
真正决定外推对不对的是**那个常量给得准不准**。所以 Ultra_Vision 这边的下一步不是把
`r` 塞进状态量自由跑（实测静止单板下 unobservable，会发散），而是量准
`armor_radius`（板面 → 回转中心）与 `armor_y_offsets`（板心高度）。

## 8. 静止靶云台抖动：噪声来源与闸门（2026-09-29）

现象：静止靶上"估计出的模型中心一直在动"，云台上下左右明显抖。
测量手段：`tools/replay_dataset ~/real_full --dump aim.csv`（逐帧落
中心/速度/ω/瞄点/前馈/观测，静止靶下**所有非零量都是噪声**），口径见下。

链路（实车 `~/real_full`，2.2 m，48 fps，1400 帧）：

| 环节 | 静止靶上的实测值 | 结论 |
| --- | --- | --- |
| 观测（PnP）逐帧 | Δx p50 0.5 / p90 1.7 mm；Δ深度 p50 6.5 / p90 22 mm | 干净 |
| EKF 中心速度 \|v\| | 均值 88 / p90 227 / max 432 mm/s（应为 0） | **噪声大** |
| EKF ω | p50 0.95°/s / p90 3.7°/s / p99 33°/s / max 199°/s（应为 0） | **噪声大** |
| 瞄点前馈 \|ω_yaw\| | 均值 0.59°/s，max 24°/s | 直接送给云台 |
| 提前量 | 386 ms（latency+age+gimbal+飞行） | 把上面两项放大 |

放大关系（都是实测）：|v|×386 ms = 35~150 mm（2.2 m 处 1~4°）；
ω 的噪声尾巴（20~57°/s）×386 ms = 相位错 7~22°（= 25~96 mm 板位移）。

四个根因与对策（按影响排序，逐个 A/B 过）：

1. **ω 的初始协方差 P(ω,ω)=100**（σ=10 rad/s）：预测一步就生成 P(ω,sin/cos) 交叉协方差，
   重捕后第一帧的 yaw 量测把它当"转速信息"吃进去 —— 实测 ω 一帧跳到 **-199°/s**。
   → 改成 4.0（σ=2 rad/s）。同一帧只到 -6°/s。转速仍由多帧 `RotationRateEstimator`
   经 `updateOmega()` 融合（`armor_ekf.hpp::initAt`）。
2. **转速估计器会跨"量测阶跃"拟合**：位置被硬约束钉住时，对称装甲板的 PnP 姿态会在
   ±90°（1.57 rad）翻面，窗口里的中位斜率就变成 1.57/窗口 ≈ 0.8 rad/s（44°/s）。
   → 单步 ≥1.0 rad 判为阶跃：整窗重来（`rotation_rate_estimator.hpp::max_step_angle`；
   0.2 s 内的真实小陀螺最多转 0.6 rad，够不到）。
3. **静止靶闸门**（`target_selector.hpp::motion_gate_*`）：|v|<0.3 m/s 且 |ω|<0.5 rad/s
   → 提前量与云台速度前馈**都按 0**（滞回：临界带保持上次判定；真实平移 ≥0.5 m/s、
   小陀螺 ≥1.0 rad/s 立刻通过）。物理上"没在动就不该有提前量"。
   代价：0.4~1.0 rad/s 的慢速自转不做提前量，少算 r·ω·0.386 ≈ 36~96 mm。
4. **未收敛不给提前量**：`TargetEstimate::converged`（= 自上次重初始化以来 ≥3 帧量测被
   接受且未发散，对齐 sp_vision 的 `update_target_count > 3`）。

结果（同一段 `~/real_full`，只改上述四项）：

| 指标 | 改之前 | 改之后 |
| --- | --- | --- |
| 瞄点 1 s 峰峰值（yaw） | 均值 1.26° / p90 5.65° / max 8.22° | **均值 0.06° / p90 0.11° / max 0.55°** |
| 瞄点逐帧 Δ（yaw） | p50 0.015° / p99 2.75° / max 6.48° | p50 0.005° / p99 0.11° / max 1.82° |
| 瞄点前馈 \|ω_yaw\| | 均值 0.59°/s / max 24°/s | p50 = p90 = **0**（98.7% 的帧判静止） |
| 估计 vs 观测 | 0.16~0.19 mm | 0.19 mm（不变） |
| 重投影 | 5.4 px | 5.4 px（不变） |
| 板号（瞄的那块）切换 | 3 次 / 912 帧 | 0 次 |

同一份数据上重做硬约束 A/B（现在四个根因都已修）：ON = 1 s 峰峰 0.06/0.11°，
OFF = 0.23/0.56° 而且"估计 vs 观测"退化到 9.6/77 mm、重投影 7.2/50 px
→ 硬约束现在是**既准又稳**（之前它"又准又抖"是 1~3 号根因在放大它注入的噪声）。

未修完的两处（已知、量过）：

* `~/real_full` 里 t=11.0~11.5 s 这一段，**观测本身**在 0.4 s 内漂了 ~130 mm
  （PnP 深度在小板/模糊/44% 检出率下的慢漂），硬约束忠实跟随 → 这一段还有
  1.5~3.9° 的单帧跳变。属于观测质量，不是估计器；换清晰数据应复测。
* 长时间丢失后重捕的第一帧仍会有一次 ~50 mm 的中心校正（滑行时按噪声速度漂出去，
  再被观测拉回）。要压掉得给硬约束的校正加速度限幅（未做，等有干净数据再定）。

## 9. 真机"识别到板就朝一个方向一直转"：下发符号（2026-09-29）

现象：一识别到真实装甲板，云台就朝右边持续转一段时间/角度。

原因：**只反读了回传符号，没反写下发符号**，闭环符号反（正反馈）。
下位机的命令帧与回传帧必须是同一个坐标系 —— 它拿 `error = cmd − current` 做闭环
（`visual_task.c` 里 `CV_EV.yaw = tj_r.yaw` 之后直接与 `cv_st.current_yaw` 比较），
所以 `yaw_sign = -1`（回传编码器 yaw 与本项目"正 yaw = 右转"相反）意味着
**下发的 yaw 也得取反**。原来 `node.cpp` 的 `pipe_send` 原样把内部角度发出去
（`camera_pose.yaw = yaw_sign·gimbal_state.yaw` 只在读的那一侧做了转换），
于是下位机收到的"目标角"是镜像的 → 误差永远朝同一侧 → 一直转，直到目标出画丢失。

修法：转换收到**一个**边界（`node.cpp` 的 `pipe_send`，瞄准/心跳/速度前馈都从这里出去）：
`cmd_yaw = command_yaw_sign · yaw`（含 `yaw_vel`/`yaw_acc`），pitch 同理。
配置在 `configs/serial.yaml`：`command_yaw_sign` 默认 = `yaw_sign`（同坐标系），
`command_pitch_sign` 默认 +1。

量法（真机，跑 auto_aim 之前单独跑，只动 3°/1.2 s，结束强制 mode=0）：

```
./build/gimbal_sign_probe --pitch      # 打印"命令 ↔ 回传"同号/反号 + 该填的值
```

对照：sp_vision 的 aimer 输出 `yaw = atan2(aim.y, aim.x) + yaw_offset` 是**它读到的同一个
IMU 系**（`io/gimbal` 回传的 yaw 与它下发的 yaw 同一坐标系），所以它不需要任何符号转换；
它用 `yaw_offset` 修的是系统性零偏，不是符号。我们这台车的编码器角度与 IMU 系反号，
就必须"读写都反"。

## 10. 下发命令的坐标系：C 板闭环比的是 IMU 世界系角（2026-09-29 量定）

现象：实车上识别到装甲板后云台朝一个方向转一段时间/角度（不是"一直加速"，是跑到错的目标点）。

量法（`tools/gimbal_sign_probe`，逐层排除；每次都要**清空云台活动范围**）：

| 步骤 | 命令 | 结果 | 说明 |
| --- | --- | --- | --- |
| A 不发 | — | ~0° | C 板没有自己的自瞄逻辑，命令通道有效 |
| B 发**回传电机角**的当前值 | `yaw=raw_now` | 动 −63°（另一次 +28.5°） | 闭环比的对量 ≠ 回传 yaw |
| `--q` 只读 | — | \|q\|=1.000 平滑；基轴 x 的方位 ≈ raw_yaw−90°，俯仰 ≈ raw_pitch−2.3° | 四元数可用；IMU 相对电机系转了 ~90° |
| `--world` | `(+az_x,+el_x)` | yaw 偏 0.6~1.2°（保持） | **世界项 yaw = +az_x** |
| `--world` | `(−az_x,·)` | yaw 跑 57.8/64.7° | 排除 |
| `--world` | `(·,−el_x)` | pitch 偏 0.2~0.8°（+el_x 跑 17.4°） | **世界项 pitch = −el_x** |
| `--world` | 电机系原样（对照） | yaw 跑 35.7° | 确认旧口径错 |
| 台阶 | `cmd_yaw+10°` | 电机 yaw **+9.18°** | 折 1:1 同号 |
| 台阶 | `cmd_pitch+10°` | 电机 pitch **−9.45°** | 折 1:1 反号 |

结论（这也是为什么 sp_vision 能直接用这套协议）：下位机的 yaw/pitch 闭环比较的是
**云台 IMU 的世界系角**（基轴 x 的方位角 `az_x`、俯仰角 `el_x`，pitch 取反），
不是回传帧里的电机编码器角；两者差一个约 90° 的安装旋转 + yaw 反向。

实现（`src/auto_aim/node.cpp` 的 `pipe_send`，唯一转换点；世界角由
`control/gimbal_command_frame.hpp::imuWorldAngles()` 从四元数算）：

```
cmd_yaw   = +az_x            + (gain_yaw_sign / yaw_sign) · Δ(内部 yaw)
cmd_pitch = −el_x            +  gain_pitch_sign           · Δ(内部 pitch)
```

Δ 是"本次要发的内部角 − 当前姿态角"，所以**不需要标定任何零点常数**（实测基准来自
当前四元数）；换机器人只重量 `configs/serial.yaml` 里那四个符号即可
（`gimbal_sign_probe --world` 直接给结论）。没有 IMU 样本的那一拍**不发**（保持），
不允许退化成"发内部电机角"的错口径。

安全开关：命令坐标系没量准之前用 `ULTRA_VISION_DISABLE_CONTROL=1 ./build/auto_aim`
只跑识别（云台只收 mode=0 心跳）。

## 12. 下位机命令帧定案：读电控源码（2026-09-29）

前面靠"探针+推理"在命令帧上反复翻车（hold 测试对约定不敏感、台阶测试被相位间残留运动污染），
最后直接读这台车的电控源码 `wheel_leg_2/gimbal/application/` 定案：

```c
// gimbal_task.c：absolute_angle 来自 INS（陀螺），不是电机编码器
feedback_update->gimbal_yaw_motor.absolute_angle   = *(gimbal_INT_angle_point + INS_YAW_ADDRESS_OFFSET);
feedback_update->gimbal_pitch_motor.absolute_angle = *(gimbal_INT_angle_point + INS_PITCH_ADDRESS_OFFSET);
// visual_task.c：回传的就是它
tj_t.yaw = gimbal_control.gimbal_yaw_motor.absolute_angle;
tj_t.pitch = gimbal_control.gimbal_pitch_motor.absolute_angle;
// gimbal_task.c：视觉值是**绝对角目标**，角度环反馈是同一个 absolute_angle
Gimbal_Yaw_Vision_Data_Target   = rad_format(CV_EV.yaw);
Gimbal_Pitch_Vision_Data_Target = rad_format(CV_EV.pitch);
Pitch_Apid_Out = pid(pitch_angle_pid, gimbal_pitch_motor.absolute_angle, Pitch_Control_Data);
// 常量
float Yaw_Vision_Plus = 1.0f, Pitch_Vision_Plus = 1.0f;      // 1:1
float Yaw_Divide_Plus_x = 0.003f, Pitch_Divide_Plus_x = 0.003f;   // 步长 rad
#define GIMBAL_CONTROL_TIME 1                                 // 1ms → 最大 ≈172°/s
#define Pitch_Max_Angle -0.49f   #define Pitch_Min_Angle 0.27f   // 软限位 [-28.1°,+15.5°]
```

结论：**命令 = 回传的那个绝对角，1:1、绝对角、无镜像、无零点常数**（和 sp_vision 同构）。
我们的内部约定是 `yaw_internal = yaw_sign·回传 yaw（= -回传）`、`pitch_internal = 回传 pitch`，
于是配置就是 `command_frame: motor` + `command_yaw_sign = -1` + `command_pitch_sign = +1`；
`yaw_vel/pitch_vel` 同样按这两个符号补（下位机是加在陀螺速度环上的前馈）。

另外两条必须与下位机对齐（已写进 `configs/tracker.yaml` 的 gimbal 段）：

* **pitch 软限位 [-28.1°, +15.5°]**：上限只有 +15.5°，靶板举太高本来就打不到 ——
  "顶到限位回不来"里有这种情况，属于机械/限位事实，不是控制 bug；
* **最大角速度 ≈172°/s**（固定步长 0.003 rad / 1ms）：我们自己的轨迹限速/提前量估算
  必须用它，否则会出现"我们规划得比机器快 → 实际永远滞后 → 看起来响应慢"。

之前那些"方向反了/一路顶限位"是两件事叠加：① 我把命令帧当成未知量去推几何映射（已作废，
代码保留在 `command_frame: world` 分支仅作对照）；② 观测的姿态时间基错配（已修：姿态取
曝光时刻）。两者都修掉之后，命令就是**回传角的直接目标**。

## 13. "转飞"根因：选板器依赖未收敛的 yaw 状态（2026-09-29 实测）

现象：板从画面边缘进入、一旦识别到，云台立刻朝**相反方向**转，板出画。

取证（`~/t1` 实车录制 662 帧、38% 帧有识别；回放逐帧比对）：

| 量 | 值 |
| --- | --- |
| 识别到的板 `obs_id` | 2 号（32/35 帧） |
| 实际瞄的板 `aim_id` | 1 号（15 帧）、无有效瞄点（18 帧）、2 号（**仅 2 帧**） |
| `obs_id == aim_id` | **4 / 35** |

`aim_id=1` 而 `obs_id=2` = 瞄到了模型里**相邻 90° 的那块板**。原因：选板器
（`TargetSelector::select`）要用**模型 yaw 状态**推算四块板各自的角度再挑"即将进入射界"的
那块；而 yaw 状态在刚入靶/刚重捕/检测断续时还没收敛 → 挑错板 → 瞄点差十几到几十度 →
云台追着一个**不存在的板**转 → 真板出画 = "转飞"。同类问题也解释了 `aim_id=-1`
（选不出可用板，只能滑行）。

修法（`src/auto_aim/control/aim_pipeline.cpp`）：

1. **静止靶 + 有新观测 ⇒ 直接瞄"刚观测到的那块板"**（硬约束已把模型该板钉在观测上，
   观测本身就是最准的瞄点），带弹道下坠补偿；不经过"四块板里挑一块"，因此不依赖 yaw 状态。
2. **没有新观测的帧 ⇒ 保持上一拍瞄点**，不用滑行的模型状态重新选板（那正是"识别一断就
   跳到相邻板、云台瞎转"的来源）。
3. `max_control_lost_frames` 5 → 25（90fps ≈ 0.28 s）：短暂丢失时**继续由我们保持姿态**，
   不再立刻交回下位机（否则遥控摇杆/它自己的积分会把云台带走 —— 实测无识别时云台自己
   从 26° 飘到 60°）。

离线验证（同一段 `~/t1`，逐帧比"下发角 − 板在相机系的方向"）：

| | yaw 误差中位 | pitch 误差中位 | 最好帧 |
| --- | --- | --- | --- |
| 修复前 | ~+20°（瞄到相邻板） | ~+5° | — |
| 修复后（有新观测的帧） | **0.02°** | **0.03°** | 0.00~0.12° |

旋转靶仍走选板器路径（需要提前量）；下一步同样可以用"观测板 + ω·lead 旋转"把它也锚到
观测上，去掉对 yaw 状态的依赖。

## 15. 第二轮实机取证：pitch 静差的真因（2026-09-29 深夜）

数据：`/tmp/aa_curve.csv`（5783 行、带 `t`，74.6 s），日志同目录。

### 15.1 三个实测事实

1. **`mcu_pitch + 板el ≈ −4.83° ± 1.58°`（5075 帧）** —— 即
   `d(el)/d(回传pitch) = −1`：回传 pitch 升 1°，板在画面里降 1°。相机的俯仰关系是稳的。
2. **回传 pitch − 我们下发的 pitch 有 2.3° 的**中位静差**（`bias`，随机位变 0.4~3.4°）。**
3. **状态行的 `aim_err` 恒 ≈0**：板在视轴下方 9.4° 时它显示 `0/0`，而
   `FIRE mode=2` 出了 397 次、其中 260 次 `pitch_err=+0.0°` —— 因为 `aim_err` 来自
   控制器快照（"目标角 − 上一条命令"），自己跟自己比；**它不能用来判断瞄没瞄准，更不能当开火判据**。

### 15.2 为什么 pitch 会"卡住不动"（数学上闭合了）

闭环是"纯比例 + 每拍按回传角重锚"：`cmd = 回传 + off`，`off = sp·kp·err`，`err = −drop − el`。
设下位机 pitch 的静差为 `bias`（`回传 = cmd + bias`），则稳态：

```
Δel = kp·err − bias = 0   ⇒   err = bias / kp = 2.5·bias
```

实测 `bias≈2.3°` ⇒ 预测 `err≈5.6°`；实测卡住段 `err≈4.7~5.6°`（`el≈−5.6~−9.4°`）。
**方向和量级都对上了：不是符号反了，是"没有积分就消不掉静差"。**

静差从哪来（电控源码，全部可核对）：

* `gimbal_task.h`: `Gimbal_Pitch_Vision_Angle_Ki = 0`、`_IMaxout = 0`、
  `Gimbal_Pitch_Speed_Ki = 0`（yaw 角度环 Ki 也是 0，但 yaw 没有重力，所以残差只有 0.33°）。
* `gimbal_task.c:1873`: 重力补偿 `pitch_gravity_conpen()` 的**调用是注释掉的**
  （函数本身还写着，`gimbal_task.h` 里 `gravity_conpen_k_*` 也在）。
  Ki=0 + 无重力前馈 ⇒ 必须靠"角度误差 × Kp"产生保持电流 ⇒ 一定存在静差。
* 顺带：`Gimbal_Yaw_Vision_Angle_Kd=2100`、`Gimbal_Pitch_Vision_Angle_Kd=1200`，
  角环输出是**陀螺角速度设定**，再串速度环；pitch 的 `motor_gyro` 用 IMU 的 y 轴陀螺。

### 15.3 本轮改了什么（我方）

| 改动 | 依据 |
| --- | --- |
| **图像闭环加积分项** `off = sp·(kp·err + ki·∫err)`，`ki=2.0/s`（`ULTRA_VISION_SERVO_KI`），积分等效偏置限 ±10°，长断流后减半 | §15.2：稳态误差 = 2.5·bias，只有积分能消掉 |
| **权限看门狗只对 yaw 生效**（pitch 阈值放宽到 12°） | pitch 的 2~3° 静差本来就不是"没权限"；上一版把它判成没权限，反而把该积累的补偿一次次清零 → 实测 pitch 卡死在 el≈−9.4° |
| **开火闸门改用图像残差**（`img_err` ≤ 1.0°，新鲜度 0.25 s，`ULTRA_VISION_FIRE_ERR_DEG`），状态行新增 `img_err=…` 与拦截计数 | §15.1-3：397 次开火里有 260 次是在残差为 0 的假象下打出去的 |
| 曲线新增**下位机陀螺角速度**两路（`mcu_*_gyro [deg/s]`） | 要判断"发一个角增量它往哪边动"，角度不够，得看它自己的速度环反馈 |
| 轴符号探针的 yaw 窗口失效（1.0 s 里检测还没恢复，测得 Δaz=−0.003°） | 需要更长窗口 + 双向台阶，下轮再压 |

### 15.4 需要电控侧配合的两件事（这才是 pitch 的根）

1. **把 `gimbal_task.c:1873` 的重力补偿调用打开**（或给 pitch 角度环加 Ki 并把
   `IMaxout` 从 0 改大）：pitch 才能真正"锁"在指定角度，否则永远有 1~4° 静差，
   而且它随姿态变化 —— 我们只能靠图像积分慢慢补，收敛要好几秒。
2. **`tj_t.mode` 现在是硬编码 `1`**（`visual_task.c: McuToNuc()`），
   视觉端根本看不到下位机真实的 `operate_mod_set`（0 手操 / 1 辅瞄 / 2 纯视觉）。
   建议改成上报 `operate_mod_set`；否则"命令没被跟随"到底是"没进接管"还是"动态静差"
   只能靠猜（这次就是靠 3 个观测量拼出来的）。

### 15.5 下一轮看什么

`img_err` 是否被积分项压到 ≤0.5°；pitch 是否几秒内收敛（而不是十几秒）；

## 16. "误差一直累积到飘飞"的真因：环路增益 × 延迟（2026-09-30）

现场观察（用户）：**开机就是纯视觉接管 → 能收敛；先遥控、再拨到纯视觉 → 飘飞**，
而且 pitch 一路顶限位。用已有曲线验证这个观察（run2，74.6 s）：

| 量 | 我们的命令摆幅 | 回传摆幅 | 图像误差摆幅 |
| --- | --- | --- | --- |
| yaw | 40.9° | **78.6°**（≈2×） | 30.9° |
| pitch | 10.9° | **47.1°** | 10.4° |

图像误差在**变坏**：`|az|` 中位 前半段 1.2° → 后半段 9.7°（8 倍）。
即"命令小幅摆动、执行机构过冲一倍、误差越来越大"—— 典型的**高增益+延迟极限环**。

### 16.1 数学

每拍把 `off = Kp·err` 加到**当前回传角**上 ⇒ 等效连续增益 `g = Kp·f_obs`（实测 f_obs≈57 Hz）。
执行机构侧延迟 τ ≈ 0.06~0.1 s（曝光+推理+下位机 172°/s 斜坡），稳定条件 `g·τ ≲ 1`：

| Kp | g [1/s] | g·τ（τ=0.1s） | 结论 |
| --- | --- | --- | --- |
| 0.5 / 0.4（原值） | 28 / 23 | **2.8 / 2.3** | 结构性振荡，误差累积 → 甩飞 |
| 0.12 / 0.10（现值） | 6.8 / 5.7 | 0.68 / 0.57 | 有 1.5~2 倍余量 |

这解释了现场现象的全部三条：

1. **开机就是纯视觉**：初始误差小、环路工作点在原点附近 → 看起来收敛；
2. **遥控→纯视觉**：接管瞬间误差大（板可能在画面边缘 20~30°）→ 环路大信号下极限环，
   幅度随误差增大 → "误差一直累积，直到超出门阀" → 飘飞；
3. **pitch 顶限位**：同样的极限环 + 下位机 pitch 的固有静差，直流分量把它推到限位。

### 16.2 本轮改了什么（我方）

* `Kp` 0.5/0.4 → **0.12/0.10**（`ULTRA_VISION_SERVO_SPEED` 仍是倍率，现场可再压）。
* **每拍步长限幅**：yaw ≤3°/拍、pitch ≤2°/拍（≈114°/s，低于下位机 172°/s 的斜坡）。
  这是抗极限环的关键 —— 单拍跳变超过"一个延迟内它能走完的量"就必然过冲。
* 偏置总幅值限幅收紧到 yaw ±30° / pitch ±20°（正常只需要几度）。
* **接管瞬间清零**：从"未确认跟随"回到"确认跟随"（= 操作手拨到纯视觉的那一刻）时，
  积分与历史偏置全部清零重来 —— 遥控阶段憋出来的量不会再一次性砸下去。
* 权限判据仍只对 yaw 生效（pitch 有固有静差，见 §15）。

### 16.3 下一轮验证点

* 遥控→纯视觉切换时：回传角**不再跳变**，`[authority] 重新获得跟随，积分/偏置清零重来` 出现一次。
* 曲线：回传摆幅应接近命令摆幅（不再是 2×），`img_err` 单调收敛到 <0.5°。
* 若仍摆动：先把 `ULTRA_VISION_SERVO_SPEED=0.5`（Kp 再减半）跑一次 —— 只调这一个量，
  不要同时动别的，便于判断 τ 到底有多大。

## 17. 更正与措施：pitch 的重力补偿其实在（2026-09-30）

**更正 §15.2**：我说"重力补偿被注释掉"是**错的**。同一个函数里另有一处**硬编码的余弦
重力前馈**直接加在 pitch 的电流设定上：

```c
// gimbal_task.c:1901
gimbal_pitch_motor.current_set = fp32_constrain(
    current_set - 8278.9217 - 14952.4009 * cos(-2.4380 + pitch_abs), -15000, 15000);
```

（被注释掉的 `pitch_gravity_conpen()` 只是另一条没启用的写法。）所以"pitch 会因重力下垂"
这个推论作废 —— 现场反馈的"pitch 有锁定"是对的。

那么 §15 里那个 **2.3° 的中位静差** 从哪来？用同样的源码推：pitch 角环 `Kp=80`、
速度环 `Kp=1500`，2.3° 误差会折算成远超限幅的电流（饱和），所以它**不该**停在 2.3° 误差上。
它之所以停住，只能是"角环的输出被别的项抵消"—— 最可能是：

* 角环 `Ki = 0`、`IMaxout = 0`（没有积分，静态必须靠误差换电流）；
* 角环 `Kd = 1200`（yaw 2100）极大，而 D 项吃的是 `目标角 − 实际角` 的微商。
  我们（视觉端）一给台阶，D 项立刻饱和 → 一次大摆；摆完停在哪，取决于饱和的方向和时长。

**所以本轮的措施是"把台阶变成斜坡"**：`pipe_send` 里对**下发命令角本身**做速率限幅
（`ULTRA_VISION_CMD_RATE_DEG` 默认 yaw 90°/s、`ULTRA_VISION_CMD_RATE_PITCH_DEG` 默认 60°/s）。
不管跳变来自接管瞬间、限幅夹取还是误差突变，下位机看到的永远是平滑斜坡，它的 D 项误差
微商就始终很小 —— 这是"转动角度还是大了"的直接对策。

观测要点：曲线里 `mcu_*` 的斜率应该 ≤ 我们设的速率；如果回传的斜率明显大于命令的斜率，
那就是下位机自己在过冲（角环 Kd/Ki 的问题），不是我们的命令。

## 18. pitch 一直"不跟/顶限位"的真因：符号反了（2026-09-30 定案）

现场现象：yaw 跟踪稳定了，**pitch 完全不跟**（并且此前反复"顶到限位"）。

两次独立测量都指向同一个符号（`d(el)/d(命令pitch) > 0`）：

| 测量 | 方法 | 结果 |
| --- | --- | --- |
| 轴符号探针（c2，闭环冻结的正台阶） | 命令 pitch +3.0° | **Δel = +3.54°** ⇒ d(el)/d(cmd)=+1.18 |
| c1.csv 全量新鲜样本回归（2799 对） | 相邻新鲜帧回归 | **d(el)/d(cmd) = +0.27** |

环路：`off = sp·kp·err_el`，`err_el = −drop − el` ⇒ `d(err)/d(off) = −(d(el)/d(off))·sp·kp`。
要负反馈必须 **sp > 0**，即 `SERVO_SIGN_PITCH = +1`。此前默认填的是 **−1** ⇒ **正反馈**：

* 误差越推越大 → `off` 一路涨 → 命令被顶到限幅端（c1 实测：命令 pitch 贴 `−28.07°`
  累计 **33.0 s**、`off_pitch` 打满 **±20°** 累计 22.7 s）→ 现场就是"pitch 完全不跟/顶限位"。
* yaw 的 `+1` 一直是对的，所以 yaw 现在稳定 —— 两轴的差别就是符号。

**为什么之前会误判成 −1**：早先那次"pitch −1 能收敛"的日志，用的是 tracker 在没有新框时
保留的**旧框**（见 §16 的 `observed_this_frame`），闭环在追一个几秒前就冻结的误差值，
看起来像收敛。测量口径修好之后，符号问题才暴露出来。

### 本轮改动

* 默认 `SERVO_SIGN_PITCH`：**−1 → +1**（`ULTRA_VISION_SERVO_SIGN_PITCH` 仍可覆盖）。
* 积分的冻结阈值 8° → 15°（幅值上限仍是 ±5°，它是负反馈里的消静差项，可以早点介入）。

### 下一轮验证

曲线里 `plate_el` 应从接管时的 ±10° 单调收到 ≈`−drop`（约 −0.9°），`img_err` 同步收敛；
如果 pitch 仍有几度静差但**方向对**，那是积分在慢慢补（下位机 pitch 角环 Ki=0），不是符号问题。

## 19. pitch"上下点头"：积分 + 静摩擦的极限环（2026-09-30）

符号修正后（§18）现象变成：yaw 收敛好，pitch 在两三度范围内以 ~1 Hz 上下点头。

机理：pitch 轴有静摩擦/死区（几度的需求才动）。控制器结构是 `cmd = 回传角 + off`
（每拍重锚），于是

1. 积分一点点涨到刚好能推动轴 → 轴突然动起来；
2. 这个执行机构的传递是过冲型（实测比值 1.5~2×）→ 冲过头，误差反向；
3. 积分再往反方向涨 …… 周期由积分增益决定（ki=2/s ⇒ ~1 s，与观测一致）。

另外，"在死区里继续输出偏置"本身也会造成点头：cmd = 回传角 + off 意味着**每拍都让
下位机再走一点**，云台永远停不下来。

### 本轮改动（三个都只作用在误差很小的时候，不影响捕获）

| 项 | 值 | 作用 |
| --- | --- | --- |
| 误差死区 `ULTRA_VISION_SERVO_DEADBAND_DEG` | 0.7° | \|err\| < 0.7° 时 off 清零（= 发"保持"），并冻结积分 —— 云台真正停住 |
| 微分项 `ULTRA_VISION_SERVO_KD` | 0.03 s | 用两次**新鲜**测量的变化率做反向修正（一阶低通），压过冲 |
| 积分 `ULTRA_VISION_SERVO_KI` | 2.0 → 1.2 /s | 放慢积分极限环；上限仍是等效 ±5° |

弹道下坠不受影响：死区是围着 `err=0`（即 `el≈−drop≈−0.9°`）开的，静差 ≤0.7°，
仍在开火闸门（1.0°）之内。

### 如果还点头

按嫌疑从大到小，一次只调一个量：

1. `ULTRA_VISION_SERVO_KD=0.06`（加大阻尼）；
2. `ULTRA_VISION_SERVO_KI=0`（先完全去掉积分，确认是不是它的极限环）；
3. `ULTRA_VISION_SERVO_DEADBAND_DEG=1.2`（把死区放宽，接受更大静差）。

## 20. 响应速度 / 丢失频率（2026-09-30）

现象：稳定之后（§18 符号、§19 点头都解决）"跟踪还不错，但响应不够快、丢目标频繁"。

两处修改：

1. **命令角速率限幅改成"随误差变化"**（原来是常数 90/60°/s）：
   `rate = clamp(8.0 × |图像误差|°, 下界, 上界)`，上界 yaw 150°/s、pitch 110°/s（仍低于
   下位机自己 172°/s 的斜坡），下界 45/35°/s。误差 >15°（捕获/目标跑掉）时用满上界，
   误差 1° 时退回下界 —— 精跟踪的平稳性不受影响，捕获速度快了约 1.7 倍。
2. **`tracker.yaml: max_lost_frames` 15 → 25**，与 `aim_pipeline.max_control_lost_frames`
   对齐。这是一条"丢目标螺旋"：tracker 先判 LOST（15 帧）→ 我们立刻停止控制 → 云台停住
   → 板自己飘出画面 → 丢得更久。对齐到 25 帧（57 Hz 下 ≈0.44 s）后，短暂的检测空洞
   会被滑行 (TEMP_LOST) 覆盖，控制不中断。

调参入口：`ULTRA_VISION_CMD_RATE_DEG` / `ULTRA_VISION_CMD_RATE_PITCH_DEG`（上限）。

若仍频繁丢失，下一步看的不是增益，而是**检测连续性**：状态行里的 `nn=` 推理速率、
`armors:` 是否为 0、以及丢目标那一刻的 `img_err`。板在画面边缘时的检测失败属于
"图像/模型"问题，不是控制环路问题。

## 21. 再提响应：Kp 上抬 + 放开捕获段步长（2026-09-30）

现场："对目标的收敛不够快，响应也不够快。"

闭环等效时间常数 ≈ `1/(Kp·f_obs)`（f_obs≈45 Hz）：

| Kp（yaw/pitch） | 时间常数 | g·τ（τ≈0.1s） |
| --- | --- | --- |
| 0.12 / 0.10（上轮） | 0.19 s | 0.54 / 0.45 |
| **0.20 / 0.16（本轮）** | **0.11 s** | **0.9 / 0.72** |

同时把"每拍步长上限"从 3°/2° 放到 6°/4°：那两档在**捕获段**才是瓶颈 —— Kp=0.12 时
20° 误差的合理需求就有 2.4°，被砍到 2°（−17%）；Kp=0.20 时需求 4°，被砍到 2°（−50%）。
平滑仍旧由 `pipe_send` 里**随误差变化**的速率限幅负责（≤150/110°/s，误差小则降到 45/35°/s），

回退手段：`ULTRA_VISION_SERVO_SPEED=0.7`（Kp 等比缩小）。

## 22. 速度前馈定符号 + "突然不收敛"到底是什么（2026-09-30）

### 22.1 速度前馈符号：−1（现场实测）

两种符号各跑一轮，现场结论：**−1 的无效摆动明显更少**（+1 等价于在速度环上同向叠加，

### 22.2 c2/c3/c4 三份曲线的统计

| 数据 | 帧/时长 | 有观测 | \|az\| 中位 (p90) | \|el\| 中位 (p90) |

| c2 | 23 s | 100% | 0.17° (6.2°) | 6.77° (9.0°) |
| c3 | 155 s | 100% | 2.61° (12.9°) | 2.44° (9.5°) |

### 22.3 为定位加了 5 列"只落 CSV 不画图"的诊断量

## 23. 闭环失控溯源：不是"没合格板"，是"速度噪声 × 提前量"（2026-10-15）

### 23.1 先排除的假设：没合格板就放弃

参考实现（sp_vision）在"没有合格板"时直接 `return {false, ...}`（不瞄不开火），于是把
我们的兜底也做成开关：`selector.no_valid_armor_policy`

* `0`（原行为）：兜底"直接瞄最后观测到的那块板"（`aim_pipeline.cpp` 的 bootstrap 分支）；
* `1`（放弃）：这一帧不产生新瞄点，云台保持上一拍瞄点，也不开火。

闭环 60 s（仿真 3 rad/s、`chase_omega_threshold=2.5`、每档 2 轮）：

| 配置 | 离轴中位 | >20.5°（半视场）帧占比 | 落盘跨度 |
| :--- | :--- | :--- | :--- |
| `policy=0` | 2.2° / 40.7° | 42% / 74% | 59.7 s / 23.7 s |
| `policy=1` | 63.0° / 85.3° | 96% / 76% | 5.6 s / 59.6 s |

而遥测计数显示 `no_plate`（选板器没给出合格板）只占 **1~3% 的帧**，`give_up` 更少。
**结论：这个条件不是失控的根因，A/B 也没有可分辨收益（差异在 run-to-run 方差内）。**

### 23.2 真正的放大器：提前量 × 车心速度噪声

给 `selector.csv` 加了 `vx,vy,vz`（提前量实际用的**平移速度状态**，世界系）之后，
同一台仿真器、同一条轨迹（真值：车**不平移**，只有 3 rad/s 自旋）：

| 档位 | \|v\| 中位 | p90 | max |
| :--- | :--- | :--- | :--- |
| 守角档（稳定） | 0.18 m/s | 1.37 m/s | 4.98 m/s |
| 追板档（失控） | 1.86~2.27 m/s | 6.1~7.5 m/s | 45.9~189 m/s |

提前量是 `latency + 观测年龄 + 云台时间 + 飞行时间 ≈ 0.35 s`，于是
**2~6 m/s × 0.35 s = 0.7~2 m 的预测偏移**，3 m 处就是 **13~38°** —— 超过 20.5° 的
半视场。一次甩出去后目标出画 → 识别断 → 状态更差，正反馈，永久失锁。

时间线里能直接看到这一拍：`t=2.4 s` 命令 yaw = **−24°**，而同一时刻真值四块板在
**+5.7°~+13.1°**（差 30°），车心估计深度同时从 2.9 m 掉到 2.03 m。

### 23.3 处置：按 |ω| 分档缩放提前量里的平移速度

`TargetSelectorConfig`：

* `lead_velocity_scale`（非旋转档，默认 1.0）：平移靶必须留 1.0，否则瞄点滞后
  `v·lead`（2 m/s、0.35 s、3 m 处 ≈ 13°）；
* `spin_velocity_scale`（旋转档，`configs/tracker.yaml` 里取 **0.0**）：预测里不叠平移，
  等价"只预测自转"；
* `spin_velocity_gate_omega`（默认 2.0，`tracker.yaml` 取 **1.0**）：门限放 2.0 会漏 ——
  自旋时 ω 估计本身会短暂掉到 1.5~1.9，那几帧 `|v|` 2~4 m/s 又进了提前量，
  60 s 里够甩一次（分档 A/B 的 rep1：32% 帧 >20.5°，其余帧正常）。

闭环 60 s A/B（同仿真器、3 rad/s、`chase_omega_threshold=2.5`）：

| 配置 | 结果 |
| :--- | :--- |
| 平移速度全用（原行为） | **6/6 次失控**：离轴中位 2.2~89.6°，42~88% 帧出视场 |
| 提前量不叠平移（全局 0） | **2/2 稳定**：中位 1.0~1.1°，0% 出视场，跨度 59.6~59.7 s |
| 分档（门限 1.0） | **2/2 稳定**：中位 1.0°，p90 2.2°，0% 出视场，跨度 59.8 s |

### 23.4 还没做的

* 速度状态本身为什么会抖到 2 m/s 量级（自旋时观测板在 ±R 圆弧上换板、关联跳变）
  —— 根修应该在 EKF（自旋档压低速度过程噪声 / 加平移速度的软先验），本轮只是
  把"噪声 × 提前量"这个放大器拿掉；
* 平移工况的干净回归：本轮试跑的平移场景（`DAEDALUS_MOVE_LOOP` ±2.4 m 横移）里靶车
  大半时间在视场外，给不出可信对比，需要单独设计（3 m 处、±0.5 m、1 m/s）。
